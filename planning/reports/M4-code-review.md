# M4 code review — uncommitted changes

Reviewed against `planning/PROMPT-SIGNALFORGE-M4.md`, `planning/reports/research-M4.md`, and `planning/reports/walkthrough-M4.md` on 2026-09-14. The implementation does **not** meet the M4 acceptance contract yet. The closeout documents' blanket PASS claims are not supported by the current code. Findings are ordered by impact; line numbers refer to this working tree.

## Findings

1. **[P0] Monthly signals can use observations that were unavailable at the decision and still execute at the next open.** `BacktestDataReader.java:335-365` checks `available_at` only for the initial evaluation month's bars. `BacktestEngine.java:800-811` evaluates later month-ends and schedules the immediately following session without checking when any required bar or action became available. `TotalReturnSignalIndexCalculator.java:70-108` also applies all loaded actions without their availability timestamps. A late-reported month-end close or revised action can therefore affect a past signal and fill. The prompt requires a frozen cutoff policy and delayed execution or rejection when data arrives after the next open. Add an integration fixture with a later-month bar/action reported after that open.

2. **[P0] The new frontend comparison flow cannot create a comparison.** `ComparisonController.java:25-34` requires `Idempotency-Key`, while `frontend/src/app/services/backtest.service.ts:378-379` posts without one. Every submission from `ResearchCompareComponent` receives HTTP 400. The same client also types the paged list as an array (`backtest.service.ts:370-372` versus `ComparisonController.java:38-45`), and the component calls `comps.length` (`research-compare.component.ts:50-58`), so existing comparisons do not load correctly. Send a durable key and unwrap/page the response.

3. **[P0] Holdout results can be disclosed without a durable exposure event.** `BacktestJobService.java:694-708` returns completed summaries with metrics from `listBacktests` without recording exposure. `ExperimentService.java:173-191` catches and logs any insert failure, so detail, comparison, and export paths can also return results after exposure persistence fails. The prompt requires append-before-read, including summary endpoints. Record exposure in a transaction before every exposing response and fail closed if insertion fails. The current test calls `recordExposure` directly rather than exercising a result endpoint (`BacktestM4IntegrationTest.java:395`).

4. **[P1] S3 does not follow the shared target-weight sizing rule.** `BacktestEngine.java:995-1002` calculates its ETF target from spendable cash after commission, although `preTradeEquity` was calculated at lines 929-942 and the prompt specifies `floor(weight × pre-trade equity / raw open)`. If S3 already holds units when it changes back to ETF, or has receivables, requested targets and shortfall are wrong. Separately, paid distributions are only reinvested in the consecutive-ETF monthly-signal branch (`BacktestEngine.java:948-992`); payment between month-ends waits for that signal instead of the next eligible open. Test both cases against independently calculated quantities.

5. **[P1] Universe versions are not validated as owner-scoped, frozen input sets.** `BacktestDataReader.java:200-212` resolves any `universe_id` directly from `universe_listings`, without checking `universes.owner_id`, `dataset_id`, `calendar_id`, or currency. `UniverseService.java:17-46` inserts the parent and members without a transaction or validating membership against the declared dataset; it can leave an immutable partial universe when a later member fails. `UniverseService.java:65-70` fabricates `XETR`/`EUR` listing details instead of reading source attributes. A run can thus reference another owner's universe or use a version against a different dataset than it declares. Validate the parent and members and make creation atomic.

6. **[P1] Strategy parameters and version identifiers are accepted without the required validation.** `BacktestJobService.java:105-177` copies the supplied strategy/version/parameter JSON into the frozen run but does not verify it against `strategy_versions`. Malformed JSON is silently replaced with defaults at lines 376-381. `BacktestEngine.java:720-726` clamps out-of-range K instead of rejecting it; an input `k=0` or `k>universe size` therefore runs a different strategy than the recorded request. The seeded S3 schema even advertises configurable `lookbackMonths` (`V8__strategy_versions_and_comparisons.sql:91`) although the V1 rule must keep ten months fixed. Reject unknown versions, unsupported parameters, malformed JSON, and invalid K before queuing.

7. **[P1] Signals and strategy catalog have broken frontend contracts.** `BacktestController.java:96-104` returns `PagedResponse<BacktestSignalDto>`, but `backtest.service.ts:334-335` and its subscription at lines 247-250 treat the response as `SignalDto[]`; the Signals tab consequently receives an object rather than an array. `research-backtests.component.ts:319-321` labels a JSON endpoint as a CSV export, and no signals CSV endpoint exists. `StrategyController.java:18-39` returns fields such as `parametersSchemaJson` and exposes only a collection, while the frontend expects `parameters`, `strategyFamily`, `status`, `supportedCalendars`, etc. (`backtest.model.ts:217-229`) and declares a non-existent detail GET. These paths should be reconciled with the actual DTOs and covered by HTTP-backed component tests.

8. **[P1] Matched comparisons do not match all required financial boundaries, and the UI expects a different DTO.** `ComparisonService.java:89-101` compares dates but not the effective funding *instant*, reporting-session sequence, benchmark accounting outputs, or execution/accounting model versions. It can mark runs matched when those differ. The backend's `BacktestComparisonDto` contains `items` and a nested `summary` (`BacktestDtos.java:628-652`); the frontend expects top-level `runIds`, `runs`, and `rollingWindowsByRun` (`backtest.model.ts:332-342`, `research-compare.component.html:102,231`). Even a directly created matched comparison cannot render its intended metrics/windows from this response.

9. **[P1] Experiment boundaries are stored without validation.** `ExperimentService.java:17-66` checks that the four date strings are present but does not parse them, require trading-session boundaries, reject reversed/overlapping development and holdout periods, or verify that the strategy, universe, benchmark, and dataset identities are compatible. An invalid or overlapping holdout can be persisted as `UNEXAMINED`, contrary to the prompt. The default `UNEXAMINED` status at line 42 is especially unsafe when no declaration was supplied; use `UNKNOWN` or require an explicit declaration.

10. **[P2] Rolling windows do not verify calendar coverage of the anniversary.** `BacktestAnalyticsCalculator.java:348-355` treats a window as complete whenever the last *run* point is on or after the fifth anniversary, then chooses the last run point on or before that date. It does not ensure the declared dataset calendar covers the anniversary boundary or that the end is the last declared session on/before it. This can report an incomplete or gapped calendar as a valid five-year window. The calculation also uses `Double` for returned compounded returns (`BacktestDtos.java:565-576`), despite the exact-decimal export requirement.

### Confirmed remaining blockers

1. **[P0] S2 run creation fails at parameter validation.** `BacktestJobService.java:179-180` queries `universe_items`; V8 creates `universe_listings`, and V9 does not create `universe_items`. After valid S2 preflight, this produces a SQL error instead of a run. The new K test uses an incomplete dataset and asserts only HTTP 400 (`BacktestM4IntegrationTest.java:530-552`), so it can pass before reaching this query. It also requires explicit `k` although the prompt sets a default of 3; `Number.intValue()` silently truncates fractional JSON numbers at `BacktestJobService.java:169-170`.
2. **[P0] Exposing an experiment run now returns an error instead of results.** `listBacktests` records access type `LIST_SUMMARY` (`BacktestJobService.java:783-785`) and signals CSV records `EXPORT` (`BacktestJobService.java:1145-1149`). V8 restricts `access_type` to `VIEW_DETAIL`, `EXPORT_DOWNLOAD`, `COMPARISON_VIEW`, or `SUMMARY_VIEW` (`V8__strategy_versions_and_comparisons.sql:136`); V9 leaves the constraint untouched. Because exposure is now fail-closed, listing any experiment run returns 500, and its signals CSV cannot download. Use the existing allowed types or a follow-on migration.
3. **[P1] Universe owner checks are bypassed on actual run paths.** The new owner-aware `validatePreflight(ownerId, ...)` is called only through its ownerless overload (`BacktestDataReader.java:170-194`). `BacktestJobService.java:120-129` and `BacktestDataReader.java:505-512` use that ownerless overload. Its guard explicitly skips checks when `ownerId == null` (`BacktestDataReader.java:242-247`). A caller can therefore use another owner's universe ID despite the walkthrough's owner-scoping claim.
4. **[P1] Downloads still do not match frontend links.** The comparison service now returns `/api/research/comparisons/{id}/export.zip` (`backtest.service.ts:395-396`), but `ComparisonController.java:55` maps `/{id}/export`. The backtests component still uses `/api/research/backtests/{id}/signals` for its “EXPORT SIGNALS” link (`research-backtests.component.ts:319-321`), even though the new CSV route is `/{id}/signals/export` (`BacktestController.java:138`). The new service helper is unused.
5. **[P1] V9 rewrites an existing immutable strategy version.** `V9__fix_strategy_schema_and_integrity.sql:3-13` drops the update trigger, changes `ETF_TREND_10M_V1` version `1.0.0`, then restores the trigger. The prompt requires old configuration versions to remain unchanged; create a new strategy version or freeze the corrected policy in a new identifier. This migration makes the old version mean something different after upgrade.
6. **[P1] Universe selections still send the wrong shape to the run API.** Backend `UniverseDto.listings` is a list of `UniverseListingDto` (`BacktestDtos.java:487-501`), whereas frontend `UniverseDto.listings` is `string[]` (`backtest.model.ts:230-245`). `research-backtests.component.ts:312-315` assigns the first listing object to `candidateListingId`; at runtime it is not a listing ID string. The strategy UI also renders these objects as listing tags. This can break S2 preflight before the K validator.
7. **[P1] The new signals CSV is unbounded and does not neutralize spreadsheet formulas.** `BacktestJobService.java:1150-1198` loads every signal/item into memory, builds one `StringBuilder`, and returns a `String` response; it has no row/byte limit. Its `csvVal` quotes commas and quotes but does not escape leading `=`, `+`, `-`, or `@` in untrusted text. This misses the prompt's bounded preparation and CSV text protection. The test exports one trusted row only.
8. **[P1] Delayed initial decisions do not move the funding boundary.** `BacktestEngine.java:748-772` records initial funding immediately before `sessions.get(0)` opens. The new scheduler can defer the first strategy signal to a later session (`BacktestEngine.java:1440-1482`), while the benchmark still begins at the original first open. That breaks the prompt's common candidate/benchmark funding and reporting boundary when initial data is late. Recompute the effective start from the actual decision instant before starting either series, or reject that timing configuration.
9. **[P1] Signal index construction still assumes bars from the start of the dataset.** `BacktestDataReader.java:534-548` loads bars from `lookbackStartDate`, but `BacktestEngine.java:707-718` and the new scheduling helper pass all dataset trading sessions to `calculateSeries`. That calculator throws on the first session lacking a loaded bar (`TotalReturnSignalIndexCalculator.java:102-107`). A run whose dataset starts before its required lookback can therefore fail even with complete required history. Restrict the session list to the loaded interval while retaining the necessary prior observation.
